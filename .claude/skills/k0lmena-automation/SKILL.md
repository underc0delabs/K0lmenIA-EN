# Automation with k0lmena

k0lmena lives in `tools/k0lmena/`. The mappers **write code once**; afterwards the suite runs without agents (and without tokens) with `npm test`.

```
tools/k0lmena/
├── web/      features/  steps/  locators/   (Playwright + Cucumber; hooks/, utils/ already exist)
├── api/      features/  steps/              (axios + Cucumber; steps/common.steps.ts already exists)
├── mobile/   features/  steps/  locators/   (WebdriverIO + Appium; support/ already exists; apps/ = .apk/.ipa)
├── performance/  k6/http/  artillery/  jmeter/   (k6, Artillery and JMeter; generated by the performance-mapper)
├── cucumber.js  run-tests.js  env.js      (env.js loads the SINGLE .env at the repo root)
```

## Names and traceability

```
+-----------+------------------------------------------+
| File      | Name                                     |
+===========+==========================================+
| Feature   | `<type>/features/US-001-<slug>.feature`  |
+-----------+------------------------------------------+
| Steps     | `<type>/steps/US-001.steps.ts`           |
+-----------+------------------------------------------+
| Locators  | `<type>/locators/US-001.locators.ts`     |
+-----------+------------------------------------------+
```

- `Feature` tags: `@US-001` and the type (`@web`, `@api` or `@mobile`).
- Tags for each `Scenario`: the ID of the source test case (`@TC-001`, `@TC-API-001`), its priority (`@critical`/`@high`/`@medium`/`@low`, the same as the source test case) and, if it's critical, `@smoke` (always lowercase: Cucumber is case-sensitive and `TAGS=@smoke` doesn't find `@Smoke`). If the source test case is a `.feature` that already has the priority tag, keep it as is.
- **Missing info**: if the test case depends on a piece of data that isn't defined (context sheet `output/context/context-US-XXX.md`, skill `context-research`), the scenario gets `@missing-info @MI-01` and the comment `# MISSING INFO (MI-01): <what is missing>` above it. It runs normally (unless it's also `@blocked`) and the k0lmena report adds a visible note to it; when publishing to Xray/QMetry/AIO, the comment says so.
- If the source is not a US (e.g. an API contract), use a slug: `api/features/pets.feature` and tag `@contract-pets`.

## Gherkin

- Keywords in **English** (`Feature`, `Background`, `Scenario`, `Scenario Outline`, `Examples`, `Given`, `When`, `Then`, `And`, `But`) and content in **English**, like the rest of the repo.
- One step = one action or one observable verification. Values that change go in quotes (`"Dinno"`) so the step is reusable.
- **Never** write credentials in a `.feature`: use a step like `When the user logs in with valid credentials` and have the step read `process.env.APP_USER` / `APP_PASSWORD`.
- A step that **could not be verified** against the real app: leave it written as the test case says, tag the scenario with `@blocked` and add a `# BLOCKED: <reason>` comment above it. `npm test` never runs `@blocked`.

## Reusing steps (mandatory)

Cucumber fails with *Ambiguous step* if two definitions match the same text. Before creating a step:

1. Search for the text in the existing definitions of the type: `grep -rn "Given(\|When(\|Then(" tools/k0lmena/<type>/steps/`.
2. If an identical or parameterizable one exists, **reuse it with the exact text** in the `.feature`.
3. Only if it doesn't exist, create it in the story's `US-XXX.steps.ts`.
4. The same step appearing in several scenarios is defined **only once**.

## Web — steps and locators

Locators: one object per story, with `LocatorInput` entries. Prioritize in this order: `role` + `name` → `label` → `placeholder` → `testId` → `text`. Only use `css` or `xpath` if there's no alternative, and comment why.

```ts
// web/locators/US-001.locators.ts
import type { LocatorInput } from '../utils/interactions';

export const US001 = {
  inputName: { placeholder: 'Name' },
  countryCombo: { label: 'Country' },
  btnSignup: { role: 'button', name: 'Sign up' },
  msgSuccess: { text: 'Signup Successful' },
} satisfies Record<string, LocatorInput>;
```

Steps: always iterate `pages` (k0lmena can run several browsers) and use the helpers, which already include waits and auto-healing. **No fixed waits**: never `page.waitForTimeout()` or the helpers' `delayMs` option; wait for something observable (`expectVisible`, `expectUrlContains(page, /…/)`, `waitForApiOk(page, /\/api\/…/)`).

```ts
// web/steps/US-001.steps.ts
import { Given, When, Then } from '@cucumber/cucumber';
import { BASEURL } from '../config';
import { pages } from '../hooks/hook';
import { click, fill, selectOption } from '../utils/interactions';
import { expectVisible, expectUrlContains } from '../utils/validations';
import { US001 } from '../locators/US-001.locators';

Given('the user is on the signup page', async () => {
  for (const page of pages) await page.goto(`${BASEURL}/signup`);
});

When('the user fills in the name {string}', async (name: string) => {
  for (const page of pages) await fill(page, US001.inputName, name);
});

Then('the user sees the successful signup message', async () => {
  for (const page of pages) await expectVisible(page, US001.msgSuccess);
});
```

Available helpers (`web/utils/interactions.ts`): `click(page, loc)`, `fill(page, loc, value)`, `selectOption(page, loc, option)`, `selectByLabel(page, label, option)`, `check` / `uncheck(page, loc)`, `hover`, `press(page, loc, key)`, `scrollIntoView`.
Validations (`web/utils/validations.ts`): `expectVisible`, `expectHidden`, `expectEnabled`, `expectDisabled`, `expectChecked`, `expectText(page, loc, text)`, `expectCount(page, loc, n)`, `expectAttribute`, `expectUrlContains(page, /fragment/)` (pass it a **RegExp**: with a string it compares the exact URL), `expectTitleIs`.

The base URL comes from `APP_URL` in the root `.env` (the app's only URL; k0lmena exposes it as `BASEURL`). In the steps use paths relative to `BASEURL`, never the full hardcoded URL.

## API — features only

`api/steps/common.steps.ts` already ships generic steps. API features are built **only with these texts** (don't write new steps unless it's impossible to express the validation):

```gherkin
Given the request uses the authentication token
Given the request uses the API key in the header "api_key"
Given the request uses the API key in the parameter "key"
Given the request uses basic authentication
Given the request sends no authentication token
Given the request uses the header "X-Tenant" with value "demo"
Given the request has the parameters:
  | status | available |
When I send a GET to "/pet/{petId}"
When I send a POST to "/pet" with the body:
  """
  { "name": "Buddy {random}", "status": "available" }
  """
When I send a POST to "/pet/{petId}" with the form:
  | name   | Buddy |
  | status | sold  |
When I save the response field "id" as "petId"
Then the response status is 200
Then the response contains the field "category.name"
Then the response does not contain the field "password"
Then the response field "status" is "available"
Then the response field "id" is the number 10
Then the response field "tags" is of type "array"
Then the response field "id" is of type "integer"
Then the response is a list
Then the response is a list with at least 1 element
Then the response has an element with "id" equal to "{petId}"
Then the response list "items" has an element with "name" equal to "Buddy"
Then the response contains the text "logged in user session"
Then the response has the fields:
  | id     |
  | name   |
Then the response header "content-type" contains "application/json"
Then the response arrives in less than 2000 ms
```

- **First summarize the spec** with `python scripts/summarize_openapi.py <url or file>` (Swagger 2.0 or OpenAPI 3.x, JSON or YAML): it gives you the `API_BASEURL`, the authentication step for each `securityScheme`, the parameters, how the body is sent (JSON, form or multipart), an example body and the documented statuses.
- **URL**: `API_BASEURL` is the spec's server **with** its basePath (`https://petstore.swagger.io/v2`) and the `.feature` endpoint is the spec's path as is (`/pet/{petId}`). Don't repeat the basePath in the endpoint (`/v2/pet` with a base that already ends in `/v2` gives a 404).
- **Authentication** according to the `securityScheme`: Bearer or OAuth2 → `the request uses the authentication token` (`API_TOKEN`); `apiKey` in a header → `the request uses the API key in the header "<name>"`; in the query → `... in the parameter "<name>"` (`API_KEY`, or `API_TOKEN` if missing); `basic` → `the request uses basic authentication` (`API_USER`/`API_PASSWORD`). Use the exact `name` from the spec (in petstore, `api_key`).
- **Each scenario creates its own data**: variables are reset in every scenario, so a `GET /pet/{petId}` first creates the pet (`POST` + `I save the response field "id" as "petId"`) in the same scenario (or in the `Background`). Never a fixed id from another run or another scenario: with `PARALLEL` or on a shared API, someone else modifies or deletes it.
- **Unique data**: `{random}` (6 digits), `{uuid}`, `{timestamp}` and `{now}` are generated once per scenario (they have the same value in all its steps): `"email": "qa+{random}@test.com"`.
- `{name}` in the endpoint, parameters, header or body is replaced by a saved value, a generated value or, otherwise, the environment variable with the same name. If a `{variable}` without a value remains in the endpoint or the body, the step fails saying which one (it isn't sent literally).
- **Body**: JSON with `with the body:` (malformed JSON fails saying where); `formData` / `application/x-www-form-urlencoded` with `with the form:`; query parameters with `the request has the parameters:` (they're encoded automatically). Multipart (file uploads) has no generic step: a `@blocked` scenario with that reason, or a custom step.
- **Types** (`is of type`): `integer`, `number`, `string`, `boolean`, `array`, `object` or `null`, as in the spec. Large integer ids (int64) are read as text so they don't lose precision: compare them with `is "9223372036854775807"`, not with `is the number`.
- Non-JSON responses (plain text) are validated with `the response contains the text`.
- Fields use dot notation (`data.items.0.id`).
- **The spec doesn't always tell the truth**: if the API responds something other than the spec (in petstore, 404 or 500 where the spec says 400), the `Then` stays with what the spec says and the scenario gets `@differs-from-spec` with a comment `# The API responds XXX; the spec says YYY`. That way, when looking at the failures, you can tell a bug or an outdated spec apart from a badly written test.
- **Public demo APIs** (petstore and similar): they are shared and change on their own. Don't assert values in listings (`findByStatus`) beyond their structure, and create every piece of data you read.

### GraphQL

The same `common.steps.ts` ships GraphQL steps. The query goes in a docstring **as is** (its braces are not interpolated); dynamic values go in the variables, which do accept `{name}`:

```gherkin
Given the GraphQL endpoint is "/graphql"
Given the GraphQL variables are:
  """
  { "code": "{countryCode}" }
  """
When I send the GraphQL query:
  """
  query Country($code: ID!) { country(code: $code) { name capital languages { code } } }
  """
Then the response status is 200
Then the GraphQL response has no errors
Then the GraphQL response contains the field "country.capital"
Then the GraphQL field "country.name" is "United States"
Then the GraphQL field "country.population" is the number 331000000
Then the GraphQL field "country" is null
Then the GraphQL field "country.languages" is a list with at least 1 element
Then the GraphQL response has an error with the message "Cannot query field"
Then the GraphQL response has an error with the code "GRAPHQL_VALIDATION_FAILED"
When I save the GraphQL field "createPost.id" as "postId"
```

- The endpoint comes from `the GraphQL endpoint is` (relative to `API_BASEURL` or a full URL) or, if not given, from `GRAPHQL_URL` in the `.env` and, if that's missing too, from `API_BASEURL` + `/graphql`.
- `GraphQL` fields are read **inside `data`** (`country.name` is `data.country.name`); the common steps (`the response contains the field "data.country"`, `the response status is`, the headers and the token) also work.
- One scenario per operation and condition; **mutations** are methods with side effects (confirmation before verifying them).

## Mobile — steps and locators

Locators: one object per story with WebdriverIO selectors. Prioritize: accessibility id (`~Log in`) → resource-id (`android=new UiSelector().resourceId("emailInput")` or `id=com.app:id/email`) → text (`android=new UiSelector().text("Sign in")`, `-ios predicate string:label == "Sign in"`). Avoid XPath unless there's no alternative.

```ts
// mobile/steps/US-001.steps.ts
import { Given, When, Then } from '@wdio/cucumber-framework';
import { US001 } from '../locators/US-001.locators';

When('the user enters {string} in the username field', async (username: string) => {
  const field = await $(US001.inputUsername);
  await field.waitForDisplayed({ timeout: 10000 });
  await field.setValue(username);
});
```

Where it runs (device, emulator or BrowserStack) is defined in the root `.env` (`MOBILE_TARGET`); the step code is the same.

## Database — verifications in the tests

`tools/db/db.steps.ts` is loaded in the web and API suites (it doesn't work on mobile yet: WebdriverIO uses its own copy of Cucumber, so don't add them to a mobile `.feature`). They are **read-only** steps that verify what a test left stored. Connections in the `.env` (`DB_CONNECTIONS` + `DB_<NAME>_*`); without a name the first one is used. **They are only added when the person explicitly asks for it** (*"add the database verification"*, *"validate that it's stored in table X"*). Even if a test case says *"the data is saved in the database"*, don't add them on your own: leave it noted as a suggestion in the mapping report (*"a DB verification can be added if requested"*). When they are requested, look at the tables and columns first with `npm run db -- schema --table <table>`: don't guess names.

```gherkin
Then the database has a record in "users" where "email" is "ana@test.com"
Then the database has no record in "users" where "email" is "ana@test.com"
Then the database has 1 record in "orders" where:
  | field   | value     |
  | user_id | {userId}  |
  | status  | PAID      |
Then the "users" record where "email" is "ana@test.com" has:
  | field      | value    |
  | status     | ACTIVE   |
  | deleted_at | (null)   |
When I query the database:
  """
  SELECT id, total FROM orders WHERE status = 'PAID'
  """
Then the query returns 1 row                 # also: "the query returns at least 2 rows"
Then the field "total" of the query is "1500.5"
When I save the field "id" of the query as "orderId"
```

- With another connection: `the database "payments" has a record in …`, `the database "payments" has …`, `in the database "payments" the … record where … has:`, `I query the database "payments":`.
- `{variable}` takes what was saved in the scenario (for example, with the API's `I save the response field "id" as "userId"`) or a variable from the `.env`. `(null)` verifies `NULL`.
- Tolerant comparison: numbers (`1500.5` = `1500.50`), booleans (`true` = `1`) and dates (`2026-10-01` matches `2026-10-01 10:00:00`).
- If the data is stored asynchronously, the steps retry up to `DB_WAIT_MS` (5000 ms by default).
- MongoDB: the table is the collection and the free-form query is a JSON: `{"collection": "users", "filter": {"status": "ACTIVE"}}`.
- Each verification attaches the query and the rows found to the report (with sensitive data masked).

## Performance — k6, Artillery and JMeter

Run it with `npm run perf -- <script> <profile>` (`run-perf.js`). Profiles: `smoke` (minimal load, validates the script), `load`, `stress`, `soak`, `spike`. Each run leaves in `reports/performance/<k6|artillery|jmeter>/` the HTML report, a small JSON summary, the raw result and the log; the console shows only the summary.

```
+------------------------+------------------------------------------+------------------------------------------+
| Tool                   | When                                     | Files                                    |
+========================+==========================================+==========================================+
| k6                     | APIs / HTTP (scales to thousands of      | `performance/k6/http/US-001-<slug>.ts`   |
|                        | users)                                   |                                          |
+------------------------+------------------------------------------+------------------------------------------+
| Artillery + Playwright | Browser flows (few users: each one is a  | `performance/artillery/US-001-           |
|                        | Chromium)                                | <slug>.yaml` + `US-001-<slug>.ts`        |
|                        |                                          | (processor)                              |
+------------------------+------------------------------------------+------------------------------------------+
| JMeter                 | APIs / HTTP when the team already works  | `performance/jmeter/US-001-<slug>.jmx` + |
|                        | with JMeter or brings a `.jmx` to reuse, | `US-001-<slug>.json`                     |
|                        | or for non-HTTP protocols (JDBC, JMS,    |                                          |
|                        | SOAP, TCP…)                              |                                          |
+------------------------+------------------------------------------+------------------------------------------+
```

### k6

```ts
// performance/k6/http/US-001-<slug>.ts
import { check, group, sleep } from 'k6';
import { env, loadOptions, request } from '../lib/k0lmena';
export { handleSummary } from '../lib/k0lmena';   // mandatory: builds the report

const BASE = env.API_BASEURL;                       // or env.BASEURL; token: env.TOKEN (API_TOKEN)
const E = { list: 'GET /users', create: 'POST /users' };   // name = method + path with {params}

export const options = loadOptions({
  vus: 50, duration: '5m',                          // target load (defined by the person)
  // ramp: '1m', soakDuration: '2h', peak: 200,     // optional
  thresholds: {                                     // defined by the person
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<500', 'p(99)<1000'],
    'http_req_duration{name:POST /users}': ['p(95)<800'],   // per-endpoint threshold
    checks: ['rate>0.99'],
  },
  endpoints: Object.values(E),                      // per-endpoint metrics in the report
});

export default function () {
  group('List users', () => {
    const res = request('GET', E.list, `${BASE}/users?page=1`);
    check(res, { 'list: status 200': (r) => r.status === 200 });
  });
  sleep(1);                                         // think time
}
```

- `request(method, name, url, body?, headers?)` adds the JSON `Content-Type` and the `Authorization: Bearer` if there's an `API_TOKEN`.
- `__ENV.X` reads any variable from the root `.env` (e.g. `__ENV.APP_USER`). Never write credentials in the script.
- Variable data: `__VU` and `__ITER` to avoid repeats (e.g. unique emails); a per-user login goes in `setup()` or at the start of the iteration.
- Don't modify `lib/k0lmena.ts`.

### Artillery + Playwright

```yaml
# performance/artillery/US-001-<slug>.yaml
config:
  target: https://app.example.com                  # the URL confirmed by the person
  engines: { playwright: { launchOptions: { headless: true } } }
  processor: ./US-001-<slug>.ts
  plugins: { ensure: {} }                          # mandatory for evaluating the thresholds
  ensure:
    maxErrorRate: 1                                # % of users who didn't complete the flow
    thresholds:
      - browser.step.Log in.p95: 3000              # <metric>: maximum (ms)
  environments:                                    # one environment per profile
    smoke:  { phases: [{ name: smoke, duration: 30, arrivalCount: 2 }] }
    load:   { phases: [{ name: ramp, duration: 60, arrivalRate: 1, rampTo: 5 }, { name: sustained, duration: 300, arrivalRate: 5, maxVusers: 20 }] }
scenarios:
  - { name: US-001 <flow>, engine: playwright, testFunction: flow }
```

```ts
// performance/artillery/US-001-<slug>.ts
export async function flow(page, _vu, _events, test) {
  await test.step('Log in', async () => {              // each step = metric browser.step.<name>
    await page.goto('/login');
    await page.getByLabel('Username').fill(process.env.APP_USER ?? '');
    await page.getByLabel('Password').fill(process.env.APP_PASSWORD ?? '');
    await page.getByRole('button', { name: 'Sign in' }).click();
    await page.getByRole('heading', { name: 'Home' }).waitFor();   // each step ends with an observable wait
  });
}
```

- Use the same selectors as `web/locators/US-XXX.locators.ts` (role/label/placeholder) if the story is already automated.
- `arrivalRate` = new users per second; `maxVusers` = cap on concurrent users. Each user is a browser: on a regular PC, more than 10-20 concurrent users saturates the machine and measures the PC, not the app.

### JMeter

Start from the template `performance/jmeter/template/template.jmx` + `template.json` (copy both and rename them `US-001-<slug>`). It requires Java 8+ and JMeter (`npm run bootstrap:jmeter`, installed in `tools/jmeter`; or `JMETER_HOME`).

The `.json` goes next to the `.jmx`, with the target, the load of each profile and the thresholds (all defined by the person):

```json
{
  "target": "API_BASEURL",
  "profiles": {
    "smoke": { "users": 1,  "ramp": 1,  "duration": 30 },
    "load":  { "users": 50, "ramp": 60, "duration": 300 }
  },
  "thresholds": {
    "error_pct": 1, "p95": 500, "p99": 1000,
    "by_sample": { "POST /users": { "p95": 800 } }
  }
}
```

- `target`: the name of a `.env` variable (`API_BASEURL`, `APP_URL`) or a URL. It reaches the `.jmx` as `${__P(base_url)}`; each request uses `${__P(base_url)}/path` in the *Path* field.
- Each profile key arrives as a property: `${__P(users,1)}`, `${__P(ramp,1)}`, `${__P(duration,30)}` in the Thread Group (with *scheduler* and loops `-1`). You can add your own keys (e.g. `peak`) and read them the same way.
- Thresholds (all in ms, except `error_pct` in %): `error_pct`, `p50`, `p90`, `p95`, `p99`, `avg`, `max`, and `by_sample` with the exact request name. They are evaluated by the k0lmena report: JMeter doesn't know about them.
- Each HTTP Request is named `METHOD /path` (it's the report's "sample") and has a **Response Assertion** with the expected code; without an assertion, a 404 counts as a success.
- Credentials: `${__groovy(System.getenv('API_TOKEN') ?: '')}` (or any `.env` variable); never written in the `.jmx`.
- Variable data: `${__threadNum}` and `${__counter(FALSE,)}` to avoid repeats (e.g. unique emails).
- `--vus` and `--duration` override `users` and `duration` for one run. Besides the k0lmena report, each run leaves JMeter's native dashboard in `<run>-dashboard/index.html`.
- If the person brings their own `.jmx`: adapt it to these conventions (properties in the Thread Group, `base_url`, `METHOD /path` names, assertions) instead of rewriting it from scratch.

## Validating what was generated (once)

From `tools/k0lmena/` (PowerShell uses `$env:REPORT_DIR="reports/validation"; $env:TAGS="@US-001"; npm run test:web`):

```bash
REPORT_DIR=reports/validation TAGS=@US-001 npm run test:web   # web: doesn't overwrite the latest npm test
TAGS=@US-001 npm run test:api      # or test:mobile (these do replace the latest report: say so)
```

- If it fails because of a badly built locator or step, fix it and run again. **2 retries at most**; if it keeps failing because of the test (you can't get the locator or the step right), tag the scenario `@blocked` with the reason and move on.
- If it fails because the app doesn't do what's expected (a real bug), **don't** change the `Then` to make it pass: leave it and report it as a possible bug (without `@blocked`, which never runs: with `# POSSIBLE BUG: <what the app does>` above it).

## Mapping report

When you finish, save `output/mappings/mapping-<US>-<type>.md` with a table (then `python scripts/format_tables.py <file>`):

```
+--------+---------------------------+---------------------------------------+-----------+----------------------------------------+
| Case   | Test case step            | Automated step                        | Status    | Note                                   |
+========+===========================+=======================================+===========+========================================+
| TC-001 | Enter the email           | the user fills in the email "..."     | Mapped    |                                        |
+--------+---------------------------+---------------------------------------+-----------+----------------------------------------+
| TC-001 | Click "Submit"            | the user clicks the Sign up button    | Adjusted  | The button is called "Sign up"         |
+--------+---------------------------+---------------------------------------+-----------+----------------------------------------+
| TC-002 | See welcome message       | -                                     | Blocked   | No message appears; possible bug       |
+--------+---------------------------+---------------------------------------+-----------+----------------------------------------+
```

Statuses: `Mapped` (same as the test case), `Adjusted` (the test case said something else and it was corrected according to the app), `Blocked` (could not be executed), `Missing info` (the step or the expected result depends on an `MI-XX`; in the note, the ID and what the app shows as an observation). If there are `Missing info` steps, add a **Missing info** section at the end with the `MI-XX` involved and their question. Close with the generated files, the validation result and the command to run it.

## Saving tokens

- Don't read the utils, hooks or `common.steps.ts` in full: the signatures are here.
- Don't navigate again or call an endpoint you already verified.
- Short final answer: generated files, validation result, blocked scenarios and the `npm` command.
