# Agent catalog

The 76 agents in k0lmenIA: what each one is for, how to ask for it, which skills, scripts, tools and connectors it uses, and what it delivers. You don't need to name the agent: Claude Code picks the right one based on your request (you can also ask for it by name).

**Legend**
- **Tokens**: *on every use* = works with the model every time you ask; *once* = generates something that later runs on its own, with no agents or tokens (`npm test`, `npm run perf`).
- **Confirms**: the agent doesn't perform the action without your explicit OK (for example, writing to a database or creating cases in Xray). Since agents can't ask questions mid-task, they return **"I need you to confirm"** and Claude asks you.
- **Connectors**: the ones enabled by default (`playwright`, `atlassian`) need nothing; the others are enabled with `npm run connector -- activate <name>` (see `CONNECTORS.md`).

## Analysis and design

### project-documenter
- **When**: when starting on a project (to build the context base) and before working on a story or epic (to gather everything there is about it), so the other agents write cases with real context.
- **Example request**: *"Document the project"* · *"Gather all the context for PROJ-12 before writing the cases"* · *"Update the project documentation"*.
- **Inputs**: the application repository (*Application repository* block of the `.env`: `REPO_PROVIDER`, `REPO_NAME`, `REPO_BRANCH`, optional `REPO_LOCAL_PATH`), the story or epic (Jira key, Azure DevOps work item or `US-XXX`) and the app URL (`APP_URL`).
- **Uses**: the repository connector, read-only (`github`, `gitlab`, `azure-devops` for Azure Repos or `atlassian` for Bitbucket Cloud): README and docs, validations, limits, messages, statuses, roles and permissions, routes, API contracts, and the story's PRs and commits; the `context-research` skill (story, comments, subtasks, epic, links, Confluence, Wiki, Figma) and public links; `npm run functional-map` (pages, menus, forms with their fields, buttons and messages, without submitting anything) and, occasionally, Playwright MCP with the `e2e-execution` skill; `scripts/documentation_index.py` and `scripts/format_tables.py`.
- **Delivers**: in `input/documentation/` (not versioned), `INDEX.md`; `project/` with the summary, repository, business rules, messages, statuses and permissions, functional map and links; `api/` with the contracts; and `stories/<US or key>/dossier.md` (story, decisions, links, PRs and code touched, screens, contradictions and testing hints). Every fact with its source. The `context-research` skill reads it first, so every agent that researches a story benefits from it.
- **Tokens**: on every use (the web walkthrough and the index are done by scripts; with `REPO_LOCAL_PATH` the code is read without the connector).

### story-analyst
- **When**: before designing tests, to find gaps and ambiguities in a story.
- **Example request**: *"Analyze story US-001"* · *"Review PROJ-12 in Jira and tell me what still needs to be defined"*.
- **Inputs**: the story (in `input/stories/`, a Jira key or an Azure DevOps work item) and its documentation.
- **Uses**: the `context-research` skill (comments, subtasks, epic, Confluence, Figma); `scripts/format_tables.py`.
- **Delivers**: `output/story-analysis/analysis-US-XXX.md` with ambiguities, risks, uncovered cases and questions for the PO; the context sheet `output/context/context-US-XXX.md` with the `MI-XX` items.
- **Tokens**: on every use.

### test-strategist
- **When**: when starting a story, feature or release, to agree on what gets tested and how.
- **Example request**: *"Put together the test plan for US-001"*.
- **Uses**: the `context-research` skill; `scripts/generate_plan.py`.
- **Delivers**: `output/test-plans/plan-US-XXX-<date>.html` (dashboard): objectives, scope, test types, risks, data and environment, entry and exit criteria, assumptions and questions.
- **Tokens**: on every use.

### manual-case-generator
- **When**: to write the test cases for a story.
- **Example request**: *"Generate the test cases for US-001"*.
- **Uses**: the `context-research` and `design-techniques` skills (equivalence partitioning, boundary values, decision tables, states, pairwise); `scripts/generate_cases.py` and `scripts/format_tables.py`.
- **Delivers**: in `output/test-cases/manual/`, `cases-US-XXX.xlsx` + `cases-US-XXX.md` + `cases-US-XXX-coverage.md` (coverage per criterion, ambiguities and questions). Cases with missing information are highlighted and carry their `MI-XX`.
- **Tokens**: on every use.

### bdd-case-generator
- **When**: to get the scenarios in Gherkin (for example, to automate them later).
- **Example request**: *"Turn US-001 into BDD"*.
- **Uses**: the `context-research` and `design-techniques` skills; `scripts/format_tables.py`.
- **Delivers**: in `output/test-cases/bdd/`, `US-XXX-<topic>.feature` (keywords and content in English, each scenario with `@TC-XXX`) + `US-XXX-coverage.md`.
- **Tokens**: on every use.

### api-case-generator
- **When**: to design the tests for an API from its contract.
- **Example request**: *"Generate the API cases for input/api/auth-endpoints.md"*.
- **Uses**: the `context-research` (if it comes from a story) and `design-techniques` skills; `scripts/summarize_openapi.py` and `summarize_graphql.py` (contracts), `scripts/format_tables.py`.
- **Delivers**: `output/api-cases/api-cases-US-XXX.md` (or `api-cases-<topic>.md` if it doesn't come from a story; `TC-API-XXX` per story or contract): a summary table and the detail of each case with method, endpoint, headers, body and expected response (positive, negative, schema and authorization).
- **Tokens**: on every use. To run them, `api-runner`; to automate them, `api-mapper`.

### test-data-generator
- **When**: to get realistic data to test with.
- **Example request**: *"Generate test data for the US-001 signup, in CSV"*.
- **Uses**: the `context-research` (the rules for each field) and `design-techniques` skills; `scripts/format_tables.py`.
- **Delivers**: `output/test-data/data-US-XXX.md` or `.csv` with valid, invalid and edge-case data. It doesn't touch any database (for that, `data-verifier`).
- **Tokens**: on every use.

### test-case-selector
- **When**: before testing a change (a PR, a release, a sprint), to know which cases to run without doing the full regression.
- **Example request**: *"Which cases should I run for PR #42?"* · *"Put together the regression for release 2.4 (main..release/2.4 in ../my-app), I have one hour"*.
- **Inputs**: the change —a git range of the application repository, a PR's files, Jira/Azure DevOps stories or issues, or the release notes— and the case inventory (manual, BDD and automated in k0lmena, with their latest result, flaky tests and bugs).
- **Uses**: the `context-research` skill (to read the issues); `scripts/select_cases.py` (matches the change against the cases, using synonyms, and scores them) and `scripts/generate_selection_report.py`. Optional: `input/component-map.json` (code folders → stories).

They spend tokens on every run: they are meant for one-off cases. Anything that repeats is worth automating with the mappers.

### security-analyst
- **When**: to review the security of your own or an authorized website.
- **Example request**: *"Review the security of https://staging.your-app.com for US-001"*.

### web-pentester
- **When**: to try to compromise your own or an authorized platform (pentest / ethical hacking) and deliver a report with the findings.
- **Example request**: *"Try to hack https://staging.your-app.com and send me what you find"*.
- **Uses**: the `e2e-execution` and `context-research` skills; OWASP ZAP in active mode (Docker), `tools/zap/scan.py --active`, Playwright MCP for manual verification (OWASP Top 10) and `scripts/generate_security_report.py`; relies on `permissions-tester` and `form-tester`.
- **Delivers**: in `output/security/<US or host>/<date>/`, `security-report.html` (active mode), `pentest-report.md` (manual findings with steps to reproduce and the fix), `zap.json` and `analysis.json`.
- **Confirms**: the URL (in `SECURITY_AUTHORIZED_URLS`), the authorization for the active scan (`PENTEST_AUTHORIZED=yes`), the environment (no production without written permission) and the scope. It is not destructive: no DoS, no massive brute force, no deleting data.
- **Tokens**: on every use (the active scan and the manual verification).

### permissions-tester
- **When**: to verify that each role sees and can do only what it should (before a release, when adding a role or a protected screen).
- **Example request**: *"Test the admin, operator and guest permissions on https://staging.my-app.com"* · *"Can an operator get into the admin panel by typing the URL?"*.
- **Inputs**: the URL (`APP_URL`), the roles and their credentials in the `.env` (`PERMISSIONS_ROLES`, `PERMISSIONS_<ROLE>_USER`/`_PASSWORD`/`_TOKEN`), optional endpoints and the expected rule (`input/documentation/project/statuses-and-permissions.md`, the dossier or the story).

- **Delivers**: in `output/permissions/<US or host>/`, `permissions-report.html` (role × route and role × endpoint matrix, differences from what is expected, findings with screenshot, which menus and buttons each role sees, Missing info and the evolution across runs), `permissions.json` and `screenshots/`. It doesn't store credentials.
- **Tokens**: on every use (the walkthrough and the matrix are done by the script).
- **Confirms**: any click on buttons with side effects, and running against production.

### resilience-tester
- **When**: to find out how the interface reacts when something fails underneath: the API goes down or is slow, the network drops, or resources don't load.

- **Inputs**: the URL or pages (`APP_URL` by default), the scenarios (all by default) and, optionally, the API pattern and the story.
- **Uses**: `npm run resilience` (Playwright intercepts the network from the browser: API with 500, 503 or 404, timeout, slow network, offline, empty responses, broken JSON or null fields, and static assets that don't load), manual exploration with Playwright MCP (`e2e-execution` skill), the `context-research` skill to know what is expected for each failure, and `scripts/generate_resilience_report.py`. For **server-side chaos**, `npm run toxiproxy` (`tools/resilience/toxiproxy.py`): it injects latency, outages and slowness into real dependencies (database, API, cache) with Toxiproxy.
- **Delivers**: in `output/resilience/<US or host>/`, `resilience-report.html` (page × scenario matrix, blank screens, silent failures, infinite spinners, technical messages, JavaScript errors, retries and recovery, with a screenshot of each scenario; plus the server-side chaos scenarios), `resilience.json` and `screenshots/`.
- **Confirms**: **server-side chaos** has a real effect → QA only, confirmed, with `reset` when done. Browser chaos doesn't submit forms or generate load against the server.
- **Tokens**: on every use (the simulation and observation are done by the script).

## Automation with k0lmena

They write the automation **once**; after that it runs with no agents or tokens via `npm test` or `npm run perf`.

### web-mapper
- **When**: to automate web cases.
- **Example request**: *"Automate the US-001 cases in k0lmena against https://your-app.com"*.
- **Uses**: the `k0lmena-automation`, `e2e-execution` and `context-research` skills; the `playwright` / `playwright-headless` connectors; k0lmena web (Playwright + Cucumber).
- **Delivers**: `tools/k0lmena/web/features/US-XXX-<topic>.feature`, `steps/US-XXX.steps.ts`, `locators/US-XXX.locators.ts` and `output/mappings/mapping-US-XXX-web.md`. Run it with `npm run test:web`.
- **Confirms**: headed or headless, if you didn't say.
- **Tokens**: once.

### api-mapper
- **When**: to automate API tests from a Postman collection or a Swagger/OpenAPI spec.
- **Example request**: *"Automate the /pet endpoints of https://petstore.swagger.io/v2/swagger.json"*.
- **Uses**: the `k0lmena-automation`, `context-research` and `design-techniques` skills; k0lmena api (axios + Cucumber, generic steps).
- **Delivers**: `tools/k0lmena/api/features/*.feature` and `output/mappings/mapping-<US or contract>-api.md`. Run it with `npm run test:api`.
- **Confirms**: the scope and the methods with side effects (POST, PUT, PATCH, DELETE) before calling them.
- **Tokens**: once.

### mobile-mapper
- **When**: to automate cases for an Android or iOS app.
- **Example request**: *"Automate the US-005 cases on the Android emulator"*.
- **Uses**: the `k0lmena-automation` and `context-research` skills; the `appium-mcp` connector (enabled with `npm run connector -- activate appium-mcp`); k0lmena mobile (WebdriverIO + Appium).
- **Delivers**: the story's `tools/k0lmena/mobile/features`, `steps` and `locators`, and `output/mappings/mapping-US-XXX-mobile.md`. Run it with `npm run test:mobile`.
- **Tokens**: once.

### performance-mapper
- **When**: for load, stress, soak or spike tests.
- **Example request**: *"I want to run a load test on the login"*. First, Claude guides you step by step with the `performance-guide` skill (test type, tool, users, ramp-up, duration, thresholds).
- **Uses**: the `performance-guide` and `k0lmena-automation` skills; k6, Artillery + Playwright or JMeter; `scripts/generate_performance_report.py`.
- **Delivers**: the script in `tools/k0lmena/performance/`, the plan and the report (metrics, charts, findings, recommendations) in `output/performance/US-XXX/`. Run it again with `npm run perf -- <script> <profile>`.
- **Confirms**: every run with load.
- **Tokens**: once (plus the analysis of the report).

### data-verifier
- **When**: to check what the tests left saved, or to verify a value in a database.
- **Example request**: *"Check in the database whether the user ana@test.com exists"* · *"Add the database verification to the signup scenario"*.
- **Uses**: the `k0lmena-automation` skill (database steps); `npm run db` (PostgreSQL, MySQL/MariaDB, SQL Server, MongoDB).
- **Delivers**: the answer in the chat (and `output/data-verifications/` if you ask for it); the DB steps in the `.feature` only if you ask for them.
- **Confirms**: every write (and it never writes to production).
- **Tokens**: on every query; the verifications in the `.feature` files, once.

### failure-analyst
- **When**: when `npm test` fails, to separate real bugs from broken, flaky, data or environment tests.
- **Example request**: *"Analyze why npm test failed"* · *"Which of these failures are bugs?"*.
- **Uses**: `scripts/analyze_failures.py` (classifies, recovers screenshot, video and trace, compares with retries) and `scripts/generate_failures_report.py`; the `e2e-execution` skill to reproduce by hand if needed.
- **Delivers**: in `output/failures/<US or suite>/`, `failures-report.html` (failures by cause, run history, error, evidence and what to do) and the real bugs in `output/bug-reports/`.
- **Confirms**: rerunning the failed ones (it runs against the environment) and filing bugs in Jira or Azure DevOps.
- **Tokens**: on every use.

### automation-repairer
- **When**: when automated tests fail because the screen changed (locators that no longer find the element or find several) or because of waits.
- **Example request**: *"Repair the tests that failed because of locators"* · *"Fix the US-001 automation after the redesign"*.
- **Uses**: the `k0lmena-automation` (locator conventions) and `e2e-execution` skills; `npm run repair` (reads the error and the DOM that k0lmena saves on failure, diagnoses, proposes a unique and robust locator, applies it with a backup and diff, and verifies, `tools/k0lmena/tools/repair/`) and `scripts/generate_repair_report.py`. It can start from the `failure-analyst`'s analysis.
- **Delivers**: the fixed locators in `tools/k0lmena/web/` and, in `output/repairs/<US or suite>/`, `repair-report.html` (diagnosis, change as a diff, candidates, screenshots of the original and the proposed element, verification), `changes.diff` and `backup/`.
- **Confirms**: applying the repairs that are not safe (medium or low confidence, verification steps, `.feature` data) and rerunning the scenarios. It never changes a test to cover up a bug.
- **Tokens**: on every use (the diagnosis is done by the script).

### log-analyst
- **When**: to understand what happened on the server: errors, spikes and the error behind a failed test.
- **Example request**: *"Analyze the logs from today's run"* · *"Why did TC-004 fail on the server side?"*.
- **Uses**: `scripts/analyze_logs.py` (app, nginx, Apache, JSON and syslog logs; cross-references them with the `npm test` scenarios, which save their start and end) and `scripts/generate_logs_report.py`.
- **Delivers**: in `output/logs/<name>/`, `logs-report.html` (errors and warnings per minute, signatures with their stack trace, each failed scenario with the server errors while it was running).
- **Confirms**: downloading logs from a shared server.
- **Tokens**: on every use (the grouping and cross-referencing are done by the script).
